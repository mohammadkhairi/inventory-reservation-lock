# Inventory Reservation System

A TypeScript service that prevents overselling of limited-stock products under
high-concurrency flash-sale traffic.

Backed by Postgres advisory locks and a lazy-expiry model. 500 simultaneous
reservations against `stock = 1` produce exactly **1 success** and **499
failures**, deterministically.

---

## Quickstart

```bash
# Requires Node >= 20 and Docker.
npm install
npm run db:up            # start Postgres via docker compose
npm run db:migrate       # apply migrations
npm run dev              # tsx watch on http://localhost:3000
npm test                 # full suite against real Postgres
```

Environment lives in `.env` — copy `.env.example` and edit. `DATABASE_URL` is
the only required variable.

### Try the HTTP API

```bash
curl -X POST http://localhost:3000/api/products \
  -H 'content-type: application/json' \
  -d '{"id":"sku-1","name":"T-Shirt","totalStock":1}'

curl -X POST http://localhost:3000/api/reservations \
  -H 'content-type: application/json' \
  -d '{"productId":"sku-1","userId":"user-A","quantity":1}'

curl -X POST http://localhost:3000/api/reservations/<RESERVATION_ID>/confirm

curl http://localhost:3000/api/products/sku-1/availability
```

## Architecture

```
src/
├── app.ts                    # express + middleware + mount /api
├── server.ts                 # http listen + graceful shutdown
├── index.ts                  # boot entry
├── config/
│   ├── constants.ts          # named constants — no magic numbers
│   └── env.ts                # zod-validated env; DATABASE_URL required
├── controllers/              # thin: parse → call service → sendJson
├── services/                 # inventoryService: deps-first pure orchestration
├── repositories/             # drizzle queries; namespace-imported by callers
├── routes/                   # thin: validate middleware + asyncHandler
├── schemas/                  # zod: request body/params + response
├── middleware/               # validate, asyncHandler, errorHandler, requestId
├── db/
│   ├── db.ts                 # pool + AsyncLocalStorage tx propagation
│   ├── schema/               # drizzle table definitions
│   └── migrations/           # generated by drizzle-kit
├── types/                    # Product, Reservation, ReservationState, AvailabilitySnapshot
├── utils/                    # clock, locker, http (sendJson), logger
└── errors.ts                 # DomainError + subclasses; mapped to HTTP status
```

**Layered flow (top → bottom):**

```
route → controller (thin) → service → repository → drizzle → postgres
```

- **Route**: `validate({ body, params })` middleware, then `asyncHandler(controller.fn(deps))`.
- **Controller**: reads the pre-validated request, calls a service function, hands the payload to `sendJson(res, responseSchema, data, status)`.
- **Service**: pure orchestration. Takes `deps` first (`fn(deps, args)`), acquires locks, reads/writes repos, applies the pure rules colocated in the same file.
- **Repository**: individual `export async function`s that use the module-level `db()` handle. Consumed as `import * as products from './productRepository.js'`.
- **DB**: `db()` returns the current tx (via AsyncLocalStorage) when inside `locker.withLock`, otherwise the pool.

**Composition happens in one place:** `src/routes/index.ts` builds `serviceDeps` and passes it to controllers. `app.ts` stays free of wiring.

### FP style (not OO)

- No classes. No `new`. No singletons for controllers/services/repos.
- Every layer exports **individual functions** (`export async function`), not a factory returning an object.
- The **DB pool is the only singleton** — initialized once in `app.ts` via `initDatabase()`.
- Types are shared vocabulary in `src/types/`; the dependency direction is `repositories → types`, `services → types + repositories`.

### Zod validation on request and response

- **Request body + params**: `validate({ body, params })` middleware runs before every handler. Schemas live in `src/schemas/`.
- **Response**: `sendJson(res, schema, body, status)` re-validates the outgoing shape. A failure here is a server bug (contract drift) — it throws a plain `Error` and lands on the **500** branch, not the 400 branch reserved for bad client input.

## Concurrency: Postgres advisory locks

Every read-then-write path (`reserve`, `confirm`, `cancel`, `getAvailability`)
runs inside `locker.withLock(productId, fn)`. The locker:

1. Opens a Postgres transaction.
2. Takes an xact-scoped advisory lock via
   `SELECT pg_advisory_xact_lock(hashtext(productId))`.
3. Stashes the transaction handle in `AsyncLocalStorage` so every repository
   call inside `fn` transparently participates in the tx via `db()`.
4. Commits (releasing the lock) when `fn` resolves; rolls back on throw.

**Properties:**

- **Overselling is impossible.** The lock is per-product, so operations on
  different products run in parallel while operations on the same product
  serialize. Granularity matches the invariant.
- **Locks can't leak.** They're bound to the transaction — a crashed process
  drops the lock automatically at COMMIT/ROLLBACK.
- **Repos don't need a `tx` parameter.** AsyncLocalStorage carries it through
  the async subtree.

### Why advisory locks over `SELECT ... FOR UPDATE`?

Both work. Advisory locks are cheaper (no row scan), work across tables, and
give us a single per-`productId` waitpoint regardless of how many rows or
tables the operation touches. The tradeoff is that they're a semaphore, not a
row lock — you have to remember to take them. We do, in `locker.withLock`.

## Expiry: lazy, no timer

Availability correctness **never depends on a background job**. Every
reservation carries `expiresAt`; the `effectiveState` function treats an
ACTIVE reservation past its expiry as EXPIRED for availability math,
regardless of what's persisted.

- Timers, restarts, and clock skew can never cause a phantom hold.
- Tests use `ManualClock` + `clock.advance(...)` — no `setTimeout`, no
  flakiness.
- No background sweeper. If persisted state is ever needed for reporting, a
  scheduled `UPDATE reservations SET state='EXPIRED' WHERE state='ACTIVE' AND
  expires_at <= now` is enough (no service call, no locks).

## Testing

Tests hit real Postgres via docker-compose.

- `tests/globalSetup.ts` creates `inventory_test` DB (if missing) and applies
  migrations — once per test run.
- `tests/setup.ts` initializes the per-worker `db()` handle.
- `tests/helpers.ts` exposes `makeHarness()` and `truncateAll()` — every test
  truncates tables in `beforeEach`.
- `vitest.config.ts` disables file parallelism (one shared DB).

```bash
npm run db:up
npm test
# 21 tests: reservation, lifecycle, concurrency (500-request flash sale), http
```

The concurrency suite is the load-bearing test — it fires 500 concurrent
`reserve` calls against `stock = 1` and asserts exactly one success and 499
`InsufficientStockError` failures.

## Migrations

Migrations are **not** applied at app startup. They run in CI/CD (see
`.github/workflows/ci-cd.yml`) via `npm run db:migrate`, which uses
`drizzle-orm/postgres-js/migrator` against the environment's `DATABASE_URL`.

Local: `npm run db:migrate` after `npm run db:up`.

---

## CI/CD

Single workflow (`.github/workflows/ci-cd.yml`):

- **push / PR to `main`**: `npm run typecheck && npm test` against a Postgres
  service container.
- **`workflow_dispatch`**: pick `staging` or `production` from the dropdown.
  Runs migrations against that environment's `DATABASE_URL` (a GitHub
  Environment secret), then deploys. Guarded to `main` — the guard aborts if
  triggered from another branch.

GitHub Environments provide per-env secrets and protection rules (required
reviewers, wait timers).

## HTTP contract

All errors return `{ "error": { "code": string, "message": string } }` with a
consistent code taxonomy from `src/errors.ts`:

| Code | Status | Cause |
| --- | --- | --- |
| `VALIDATION_ERROR` | 400 | Zod parse failure on request |
| `INVALID_QUANTITY` | 400 | Non-positive-integer quantity |
| `PRODUCT_NOT_FOUND` | 404 | Unknown productId |
| `RESERVATION_NOT_FOUND` | 404 | Unknown reservationId |
| `INSUFFICIENT_STOCK` | 409 | Requested > available |
| `INVALID_RESERVATION_STATE` | 409 | e.g. confirm on CONFIRMED |
| `INTERNAL_ERROR` | 500 | Unhandled / response validation failure |
