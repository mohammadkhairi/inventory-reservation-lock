# Architecture guide for this repo

Read this before making structural changes. These are settled patterns — the
result of several rounds of refactoring — not suggestions.

## Layered flow

```
route → controller (thin) → service → repository → drizzle → postgres
                                    ↘ rules (pure)
```

Composition happens **inside `apiRoutes()`** — nowhere else. `app.ts` only sets
up express, mounts `/api`, and serves Swagger. It does not touch repos,
services, or controllers.

## FP style, not OO

- **No classes, no `new`, no singletons** for repos/services/controllers.
- Every layer exports **individual functions** via `export async function` (or
  `export function`), never a factory returning an object with methods.
- The **DB pool is the only true singleton** — initialized once in `app.ts`
  via `initDatabase()`.
- The **locker** is a plain object literal — imported directly wherever needed.
- **No `Deps` wrapper types.** Services import repos + locker directly; they
  do not receive them as arguments.

## Directory layout

```
src/
├── app.ts                    # express + middleware + /health + /docs + mount /api
├── server.ts                 # http listen + graceful shutdown
├── index.ts                  # boot entry
├── errors.ts                 # DomainError + typed subclasses; mapped to HTTP status
├── config/
│   ├── constants.ts          # named constants — no magic numbers anywhere
│   └── env.ts                # zod-validated env; DATABASE_URL required
├── controllers/              # thin: (input, ...) → data. no res, no deps.
├── services/                 # productService / reservationService — orchestration
├── rules/                    # pure business rules (no I/O, no clock reads)
├── repositories/             # drizzle queries; namespace-imported by services
├── request/                  # zod request schemas (body / params / query)
├── response/                 # zod response schemas
├── routes/                   # thin: validate middleware → controller → sendJson
├── middleware/               # validate, asyncHandler, errorHandler, requestId, requestLogger
├── db/
│   ├── db.ts                 # pool + AsyncLocalStorage tx propagation
│   ├── schema/               # drizzle tables + pgEnums + TS enums (colocated)
│   └── migrations/           # generated by drizzle-kit
├── docs/openapi.ts           # OpenAPI 3.1 built from zod schemas
├── types/                    # Product, Reservation, AvailabilitySnapshot (no enum here)
└── utils/                    # locker, http (sendJson), logger
```

## Per-layer signatures

### Repositories — plain async functions, no deps

```ts
// src/repositories/productRepository.ts
import * as db from '../db/db.js';

export async function findById(id: string): Promise<Product | null> {
  const row = await db().query.products.findFirst({ where: eq(products.id, id) });
  return row ?? null;
}
export async function save(product: Product): Promise<void> { … }
```

Callers consume as a namespace — the module structurally satisfies the
`ProductRepository` interface:

```ts
import * as products from '../repositories/productRepository.js';
await products.save(product);
```

**Use `db().query.<table>.findFirst` / `.findMany`** (drizzle relational API),
not `select().from().where().limit(1)`. Same behavior, less noise.

### Services — deps-first, one function per operation

```ts
// src/services/reservationService.ts
import * as products from '../repositories/productRepository.js';
import * as reservations from '../repositories/reservationRepository.js';
import { locker } from '../utils/locker.js';

export async function reserve(input: ReserveInput): Promise<Reservation> {
  return locker.withLock(input.productId, async () => {
    const product = await products.findById(input.productId);
    …
    const now = Date.now();  // wall clock read directly; tests use vi.setSystemTime
    …
  });
}
```

**Services import repos + locker + `Date.now()` directly.** No `ServiceDeps`
object, no `Clock` abstraction, no factory. Split by aggregate root:
`productService` owns product-facing ops, `reservationService` owns
reservation-lifecycle ops. Each may read the other's repo when needed — a
service is "what the operation is fundamentally about," not "which repo it
touches."

### Rules — pure, no I/O

```ts
// src/rules/reservationRules.ts
export function effectiveState(r: Reservation, now: number): ReservationState { … }
export function computeAvailability(product, reservations, now): AvailabilitySnapshot { … }
```

Any function that takes `now` as an explicit argument (no `Date.now()`
inside), never touches `db`, `locker`, or the network — belongs here. If you
find yourself importing `db` or `locker` into `rules/`, you've put the wrong
thing there.

### Controllers — pure input → output

```ts
// src/controllers/reservationController.ts
export async function reserve(body: ReserveBody): Promise<Reservation> {
  return reservationService.reserve(body);
}
```

Controllers receive **already-validated, already-extracted inputs** from the
route. They **do not take `res`, `req`, or `deps`**. They call one service
function and return the data. Response shaping (status, sendJson) is the
route's job.

Yes, this makes controllers one-line pass-throughs today. The layer exists so
that when a request maps to multiple service calls or needs cross-service
composition, there's a natural home.

### Routes — validate → extract → call controller → sendJson

```ts
router.post(
  '/',
  validate({ body: reserveBody }),
  asyncHandler(async (req, res) => {
    const reservation = await reservationController.reserve(req.body as ReserveBody);
    sendJson(res, reservationResponse, reservation, 201);
  }),
);
```

Routes:

1. Attach `validate({ body?, params?, query? })` middleware (zod schemas from `src/request/`).
2. In the handler, cast `req.body` / `req.params` to the schema-inferred type — trust the middleware.
3. Call the controller.
4. Call `sendJson(res, schema, data, status)` — this validates the outgoing shape against a `src/response/` schema.

## Validation

- **Request body / params / query** — `validate({...})` middleware runs before every handler. Schemas live in `src/request/`.
- **Response** — always through `sendJson(res, schema, body, status)`. Response validation failure is a **server bug** (contract drift between service and API); it throws a plain `Error` and lands on the **500** branch, not the 400 branch reserved for bad client input.

## Concurrency

`locker.withLock(key, fn)` is the single concurrency primitive.

1. Opens a Postgres transaction.
2. Takes `pg_advisory_xact_lock(hashtext(key))`.
3. Stashes the tx in `AsyncLocalStorage`.
4. Runs `fn`. Repositories inside `fn` transparently use the tx via `db()`.
5. Commits (releasing the lock) when `fn` resolves; rolls back on throw.

**Every read-then-write path takes the lock.** No exceptions. Overselling is
impossible only because of this discipline.

**Watch out:** anything you `save()` inside `withLock` gets rolled back if you
throw afterwards. Don't try to "save then throw" — the save is a no-op.

## Types and errors

- **Types** live in `src/types/` (data shapes only). Repos, services, rules import from here.
- **Enums** (pgEnum + matching TS enum) live in their resource's schema file (e.g. `src/db/schema/reservation.ts`) — never a separate `enums.ts`. Colocation prevents drift. Use:

  ```ts
  const RESERVATION_STATES = ['ACTIVE', 'CONFIRMED', 'CANCELLED', 'EXPIRED'] as const;
  export const reservationStateEnum = pgEnum('reservation_state', RESERVATION_STATES);
  export const ReservationState = { ACTIVE: 'ACTIVE', … } as const;
  export type ReservationState = (typeof RESERVATION_STATES)[number];
  ```

  Consumers `import { ReservationState } from '../db/schema/reservation.js'`.
  Use `ReservationState.CONFIRMED` at value sites; use `typeof ReservationState.CONFIRMED | typeof ReservationState.CANCELLED` for type unions. **Never inline string literals** like `'ACTIVE'`.

- **Errors** live in `src/errors.ts` at the root. `DomainError` subclasses carry an `ErrorCode`; `errorHandler` middleware maps codes to HTTP status. New error → add code to `ErrorCode` + status in `STATUS_BY_CODE`.

## Constants — no magic numbers

Every raw number goes into `src/config/constants.ts` with a named identifier.
Time-unit multipliers (`MS_PER_SECOND`, `SECONDS_PER_MINUTE`) are file-private
so callers see intent, not arithmetic.

## Environment

- `src/config/env.ts` uses zod. `loadEnv()` is idempotent (cached).
- `DATABASE_URL` is **required** — no fallback, no in-memory mode.
- DB pool sizing (`DB_POOL_MAX`, `DB_IDLE_TIMEOUT_S`, `DB_MAX_LIFETIME_S`, `DB_CONNECT_TIMEOUT_S`) is env-configurable with sane defaults from `constants.ts`.

## Migrations

**Not applied at app startup.** CI/CD runs `npm run db:migrate` per environment
(see `.github/workflows/ci-cd.yml`). Local dev: run manually after `npm run db:up`.

## Testing

- Tests hit **real Postgres** via docker-compose. No mocks, no in-memory doubles.
- `tests/globalSetup.ts` creates the `inventory_test` DB + applies migrations once.
- `tests/setup.ts` inits the per-worker `db()` handle.
- `tests/helpers.ts` provides `truncateAll()` + `seedProduct()`.
- `vitest.config.ts` sets `fileParallelism: false` — tests share one DB.
- Every `describe` calls `beforeEach(truncateAll)`.
- **Time-based behavior**: `vi.useFakeTimers({ toFake: ['Date'] })` + `vi.setSystemTime(...)`. Only Date is faked; setTimeout/setInterval still run on real time so the Postgres client's internal timers keep working.

## Swagger

- OpenAPI 3.1 spec is built in `src/docs/openapi.ts` from the same zod schemas used by the runtime (via `@asteasolutions/zod-to-openapi`).
- Served at `/docs` (interactive UI) and `/docs.json` (raw spec).
- Adding a new endpoint = register the path in `openapi.ts` alongside the route + schemas.

## What NOT to do

- **No classes.** No `new SomeService()`. No factories returning objects with methods.
- **No module-level singletons for controllers/services/repos.** The DB pool is the only singleton.
- **No `Deps` wrapper types.** Services import repos + locker directly.
- **No `res: Response` or `req: Request` in controller functions.** Route handles HTTP I/O.
- **No inline raw numbers.** Add to `constants.ts` first.
- **No inline string literals for enum values.** Use `ReservationState.ACTIVE`.
- **No double validation.** Middleware validates the request; controllers trust it.
- **No `select().from().where().limit(1)`.** Use `db().query.<table>.findFirst({ where })`.
- **No auto-migrate at boot.** CI/CD handles it.
- **No background sweepers, timers, or `setInterval` jobs** unless there's a proven need. Lazy computation is preferred.
- **No mocked DB in tests.** Real Postgres or bust.
- **No abstractions for hypothetical futures.** If it's not used now, delete it.
- **No `save`-then-`throw` inside a `withLock` block.** The transaction rolls back the save; the code is a no-op.
